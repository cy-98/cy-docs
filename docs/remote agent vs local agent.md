# Remote Agent 与 Local Agent


|      | Local                        | Remote                       |
| ---- | ---------------------------- | ---------------------------- |
| 形态   | Cursor、Claude Code、Codex CLI | Cloud Agent、后台任务、托管会话        |
| 跑在哪  | 本机，当前文件夹                     | 服务端沙箱                        |
| 交互   | 开着电脑不停对话                     | 不用一直盯界面                      |
| 能做什么 | 读仓库、跑命令、改文件、开终端；中断了也能看日志     | 拉代码、改、测、提结果                  |
| 适合   | 频繁交互、强依赖本机环境                 | 异步并行；批量改动、长跑验证、多分支试错         |
| 代价   | 占电脑资源；电脑要保持开机                | 环境、密钥要单独配；自动化测试更复杂；工具可用性要求更强 |


---

在26年初，公司推出在线 Agent，团队或者公司内部主要是还是使用 Claude-code 和 codex 这类工具。

当时在线 Agent 还是只能完成代码工作，所以我还是主要使用 Multica 来管理本地的 Agent 和多个并发需求。在线 Agent 主要做一些代码调研和审查的工作。

后来在线 Agent 升级了模型并且增加了一些 MCP，可以去阅读公司内的文档和Jira ticket。

我开始将大部分工作迁移到在线 Agent上，并且预设一些 prompt 能够像 Multica 一样基于 Jira ticket 来工作。人只需要在 Jira ticket 上描述需求， Agent 尽可能的交付一个完整的需求，最后人来review。  

这种工作模式极大的节约了我的注意力和时间，而且在下班之后还能让 Agent 继续干活。唯一要确保的就是最初的需求描述足够正确和完整。这要求我在最开始就确定这个计划在我的脑海里是自洽的，让 Agent 一步步实现计划变成了我确定计划的步骤和框架，细节由 Agent 去调研。

后来我发现 Remote Agent 的价值，很大程度看能不能交付 **需求 → 代码 → MR → 端到端验证**。只在沙箱环境中运行代码是远远不够的，还需要公司提供测试环境或者准上线环境的访问权限，文档库的访问权限，对公司各类工具的访问和操作。

在当时公司中，能否让 Agent 调用足够多的资源就是工作 Agent 化的一个卡点。

同时，因为在线Agent 很难提供代码文件到界面上，这种工作模式也让我对代码的关注度越来越弱。所以我越来越看重 Agent 如何做自动化验证，以及是否验证的足够。

Remote Agent 是未来大方向，电脑关机人睡觉了，Agent还能干活，第二天早上人来 review 成果。但是要求大环境对 Remote Agent 友好，提供足够多的公司资源。人能把积累的知识传递给 Remote Agent。

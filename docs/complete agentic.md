# 如何尽可能使用 AI 替代日常工作

从极简的问答到完整的工作交付，哪些步骤 AI 接管了？

日常工作是一条链路：

```
计划 ──▶ 编码 ⇄ 测试 ──▶ 上线
 │                         │
 └──────── 继续计划 ────────┘
```

人做三个决策：**想法**、**上线前的验证**、**上线决定**。

尽可能使用Agent替代，就是把这三个决策之外全部Agent化。


## 计划

```
想法 🙋‍♂️
  │
  ▼
知识搜索 🤖  ◄──────────────┐
  │                        │
  ▼                        │
书写文档 🤖                 │
  │                        │
  ▼                        │
反复审查 🤖  ───────────────┘
  │
  ▼
确定计划
```

## 编码

```
理解计划 🤖
  │
  ▼
理解工程 🤖
  │
  ▼
程序设计 🤖
  │
  ▼
设计审查 🙋‍♂️ 可选
  │
  ▼
构建测试 🤖  ◄──────────────┐
  │                        │
  ▼                        │
编码 🤖                     │
  │                        │
  ▼                        │
及时验证 🙋‍♂️ 可选  ──────────┘
```
如果关心代码质量， Agent 的程序设计和代码目前还需要人来review。
如果在工作流开始之前能够有明确的设计准则，或者工程有设计足够明确的定义和边界，较为完整的编码规范和设计说明，则更倾向于让 Agent 自主完成整个开发循环。


## 测试

```
部署 🤖  ◄──────────────────┐
  │                        │
  ▼                        │
数据准备 🤖                  │
  │                        │
  ▼                        │
验证 🤖     ────────────────┘
```

Agent 可以在测试环境进行自动化验证，产出足够的验证结果交由人来review。
人来做决策是否跳出测试循环。

## 上线

```
部署 🙋‍♂️
  │
  ▼
观察 🤖
  │
  ▼
报警 🤖
  │
  ▼
继续计划 ──▶ 回到「计划」
```
生产环境部署前，人都需要进行一次验证和审查，对整个 Agent 的产出结果，需要有一个人来承担责任。

## 跑通链路

对公司来说，每一步都要给 Agent 足够的工具和环境，让它能按流程稳定执行，才能顺利交付。

上面四个阶段，对应到一个常见 web 团队（产品管理、设计师、前端、后端、测试、运维），就是把每个角色手上的工具交给 Agent：

| 阶段 | 角色 | 职责 | Agent 需要的能力 |
| --- | --- | --- | --- |
| 计划 | 产品管理 | 交付 PRD，描述需求和目标，观察真实用户反馈以持续改进 | 访问文档库并创建文档（atlassian-mcp） |
| 计划 | 设计师 | 产出贴近用户的设计交互稿 | 感知用户意图并创建正确的设计稿（figma-mcp） |
| 编码 | 前后端开发 | 实现界面功能和接口开发 | 访问代码库并提交 MR |
| 测试 | 测试 | 根据 PRD 确定测试范围，保证交付质量 | 自动化行为，并访问测试环境进行测试（playwright-cli） |
| 上线 | 运维 | 提供测试环境和生产环境的稳定 | 观察服务稳定性，并按规则设置报警 |

对于整个团队来说，协作工具越来越对 Agent 开放，让 Agent 可以完成各个工作的手工部分。
设计师需要将灵感快速落实到画布上,开发需要定义更多的开发规则和架构设计，让 Agent 替代手工编码的工作。
测试更需要定义明确的 case 定义，聚焦在完善测试数据和测试能力。

## 打分

整条链路跑完，还要对这一轮打分。抛开复杂的工程指标，我在维护的工程里只用五个维度。

**计划完整**

计划里要有目标、边界和工作顺序。Agent 有疑惑，就一点一点问到共识。

中途靠人补充，说明人在计划阶段想得不够。虽然人很难一次写全，所以计划阶段要尽量搜齐上下文、精炼，最后至少在脑海里是自洽的。

**工具完整**

工具不够，Agent 走不完整条链。代码权限、需求管理、测试自动化等工具缺少就不能走完交付链路。

**规则完整**

要有够用的上下文工程，和写清楚的开发准则。需求怎么推进、计划怎么写，同样要有准则。任由 Agent 自由发挥，不稳定、代码差、目标偏。

**流程完整**

从承接需求、落实计划、编码测试到验证交付，每一步怎么做、用哪套工具、逻辑是什么。

**Agent 可用**

Agent 先要能用：按人的方式调用工具；中断了能查原因、恢复上下文再试；对上下文和工作有记忆，不能裸奔。

## 结语
上述目标在一个公司中落实有难度。大厂使用自研开发套件，拓展需要协调更多资源，更多时间。
小厂因为成本问题，使用多个厂商的办公套件，更难以相互打通。提效是一个永恒不变的话题，团队管理者应该时刻思考什么样的工作模式可以最大化发挥 Agent 的优势，能够让人的注意力落实在最宝贵的地方。
